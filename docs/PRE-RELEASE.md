## 下一次另行授權後的安全順序

1. 先審閱目前全部未提交修改，確認只提交核准程式、測試與文件；正式 JSON 不混入提交。保留 DEMO-GUIDE 與既有使用者資料。
2. 唯讀核實遠端 main、最新成功 main 資料流程的 Checkpoint v2、Artifact 到期時間及免費用量。重新比較正式網站與候選的四份資料；這次表格只代表此次檢查時間。
3. 驗證 Checkpoint 的 Manifest、來源時間、Schema、SHA-256、成功 main Run 與 commit 來源；股票目錄沿用未變且驗證有效的目錄。任何一份來源日期或擷取日期倒退，都停止整合，不能用本機 JSON 補成「最新」。若已過期或缺失，另行取得更新授權，不能自動初始化或退回舊檔。
4. 優先沿用現有 **checkpoint-only** 發布：新版 main 程式搭配明確核准、仍為最新有效的 Checkpoint。`source=checkpoint`、指定核准 Run、`initialize_state=false`、`publish_current=true`。此模式不呼叫四個來源 API，也不重新初始化。既有精準選擇若判定核准 Checkpoint 已被較新有效版本取代，應停止重新核准，不能放寬保護。
5. 發布前明確授權一次發布與必要的暫時發布開關；排程及長期自動發布保持停用。新程式建置前由既有 restore 驗證並載入核准資料，完整測試、子路徑建置及公開產物檢查必須通過。本文沒有執行 restore 或修改資料。
6. 發布後逐份核對正式 JSON 與核准 Checkpoint 的雜湊、來源日期及擷取時間，確認 UI 與五份公開 JSON 正常，再恢復發布開關。若失敗停止，不能自動改用舊資料重試。
